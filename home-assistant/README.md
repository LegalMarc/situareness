# Situareness for Home Assistant

This custom integration is uncommissioned. It independently polls NWS alerts once a minute and defaults to shadow mode. Actual installation and delivery require separate commissioning. Continue to use independent official alert channels. Provider and network delays, polling, controller outages and device behavior can delay or prevent an alert.

For a future authorized installation, copy `custom_components/situareness` from this archive to Home Assistant's `<config>/custom_components/situareness`, restart HA, then add **Situareness** under Settings > Devices & services. The optional `home-assistant/situareness.example.json` is a blank starting point for the private `<config>/situareness.json` file. Keep a local working copy under `ignored-resources/` and copy it privately to HA; reload the integration after changes. The example queries NY and DC and contains no configured footprints, rules, or recipients. Never share or commit private coordinates or device identifiers.

Configure private household longitude/latitude points under `locations`, never town centers. Optional location `name` supplies the display label and `speakers` contains HA media player entity IDs. Configure `approved_rules` as exact NWS event names mapped to reviewed starting phrases of official protective instructions. Unconfigured points, absent polygons, unmatched wording, and unapproved rules cannot produce an alarm. `phones` lists HA mobile-app service names without `notify.`; `tts_entity` identifies an HA TTS entity. Rules and targets require validation before relying on them.

Both `live_enabled` and `commissioning_passed` must be explicitly true before output services can be called. Both are false in the supplied example. Leave them false until policy replay, private footprint and source verification, coordinated phone and speaker testing, and failure/stop behavior are documented and separately authorized. These settings do not themselves prove commissioning. There is no horn, Ring, police/fire panic, recipient alert acknowledgement, or repeated-reminder adapter.

New qualifying alerts target all configured phones and speakers at affected locations only. Phone service data includes the official URL and is limited to 2,800 JSON bytes; long instructions are shortened with a prompt to open the source, and large location lists can be summarized. The full instruction remains in the private outbox. Each speaker names its own location, omits the URL, and limits spoken instructions to 300 characters with a prompt to open the source link if shortened. The budget leaves provider-envelope headroom but does not establish final APNs size or delivery.

- **Collection and delivery bounds:** The integration queries NWS active GeoJSON alerts across configured states under `50`s total fetch timeout, `25`s per-page timeout, `50` pages, and `8 MiB`/page response limits, deduplicating identical feature copies without failing large multi-state bursts. It prioritizes new first-attempt targets ahead of retries and makes up to three total delivery attempts per target (`MAX_ATTEMPTS = 3`: one initial call plus up to two retries for failed or uncertain calls, not repeated reminders) within fifteen minutes (`MAX_AGE`), after rechecking the current clock before each 10-target delivery group (`100` attempts/poll, `30`-second deadline).
- **Pre-drain and serialization cost:** Near-capacity polls above `5,000` projected targets pre-drain deliverable items before queueing new plans, then deliver newly queued first-attempt items with any remaining `100`-attempt / `30`-second budget (or queue them for the next poll if exhausted). Up to 10KB instructions per outbox item serialize tens of MB across large outbox saves.
- **Unsent expirations:** Unexhausted queued targets for active (or suspended-from-active) alerts expiring via 15-minute `MAX_AGE`, backward clock rollback (`created > now`), or removed recipients in `situareness.json`, plus active-alert targets exhausting three attempts (`MAX_ATTEMPTS = 3`), increment `expired_unsent`, advance `expired_unsent_at` to the latest expiration timestamp, record `expired_unsent_reasons`, set `partial: true` and expired outcomes, and latch `situareness_degraded` for seven days from the latest expiration (resetting elapsed counts once seven days pass) or until acknowledged on reload.
- **Expiration updates, degradation freezes, and caveats:** Non-`outbox_overflow` degraded holds freeze `created` ages via `last_degraded_poll` so surviving pre-degradation retries can resume on recovery. Expiration-only updates do not trigger new alarms, `ended_or_absent` does not establish official cancellation, and a crash or save failure after Home Assistant accepts a 10-target delivery group can duplicate that group on retry. Acceptance is not proof a person heard an alert.

## Health, storage, and degraded recovery

- **Sensor state and attributes:** `sensor.situareness_monitoring` exposes `active_count`, `event_count`, `source_feature_count`, `last_success`, `shadow`, `planned_count`, `withheld_count`, `pending_count`, `deliverable_count`, `suspended_count`, `delivery_attempts`, `delivery_failures`, `expired_unsent`, `partial`, `quarantined_count`, `quarantine_ambiguous`, `cancellation_uncertain`, `evidence_degraded`, `output_blocked`, `degraded_reason`, `degraded_at`, `degraded_until`, `acknowledge_rejected`, and up to 25 redacted `events` (excluding `events`, `last_success`, `degraded_at`, and `degraded_until` from recorder history).
- **Private storage and offload:** State uses Home Assistant's `Store(..., private=True)` (`0600` when supported); async HTTP pagination runs asynchronously while per-page JSON decoding and normalization run in worker threads, post-fetch validation, reconciliation, planning, deliverable counting, and batch selection run on HA's executor, and bounded `<=10`-item per-group qualification rechecks plus `O(n)` in-memory setup, outbox, and snapshot bookkeeping run on the event loop. Persisted records validate `state`/`prior_state` (`{active, ineligible, ended_or_absent, quarantined, unconfirmed, superseded, cancelled}`), `save_id`, and `expired_unsent_reasons` / outcome `"reason"` (`{age, clock_rollback, target_removed, exhausted}`).
- **Write verification:** When Home Assistant is not stopping, each persisted save verifies its `save_id` on disk so swallowed storage write failures raise `UpdateFailed` before updating post-save poll state (`expired_unsent*`, `last_degraded_poll`, `acknowledge_rejected`); shutdown-deferred saves skip verification. Load-time rejected or no-op ISO-8601 `acknowledge_degraded_at` values and initial store-error markers update config entry data immediately on load.
- **Lifecycle and backup cleanup:** Entry removal dismisses notifications before deleting the store and `.corrupt.*` backups while keeping `situareness.json`; post-`malformed_store` recovery deletes stale `.corrupt.*` backups once saved (logging and retrying if unlink fails). Unloading stops the coordinator before unloading platforms (resuming monitoring and notification sync, including `quarantine_ambiguous`, if platform unload fails), aborts post-fetch saves/delivery once stopping, and dismisses `situareness_degraded` on failed platform forwarding or abandoned/failed initial setup retries.
- **Bounded history:** Caps are `1,000` records (`min(ts, updated + 5m) + 7d` `MAX_ACCEPTANCE_AGE` clamped at `MAX_TIMESTAMP`), `100` references/alert, `100` fingerprints/record, `5,000` unique quarantined IDs/poll, and `5,000` outbox targets. Bounded storage protects cancellation components, `active`/`cancelled`/`prior_state == "active"`/`<=15m`-bridge-action lineages, and scoped quarantined lineages even when absent, while excluding poll-wide `quarantine_all`/`unconfirmed` suspensions lacking active prior state or `<=15m` actions, ordinary `ineligible` items, and non-actionable hidden `superseded` placeholders (truncating >1,000-feature ambiguous bursts cleanly with safe snapshot fallback for evicted `ineligible` items).
- **Quarantine and continuing updates:** Scoped quarantine isolates malformed/oversized features with valid IDs while only `Actual` `Update`/`Cancel` supersede referenced alerts; continuing segments at or after a partial cancellation (`sent >= cancelled_at`) can qualify new actions while pre-cancellation retries stay suspended.
- **Evidence and storage degraded modes (`evidence_degraded: true`, `output_blocked: true`, `active_count: unknown`):** Triggered by `cancellation_evidence_overflow` (`>1,000` protected records; `degraded_until >= 7d` covering evicted component horizons up to `MAX_TIMESTAMP`), `malformed_cancellation` / `conflicting_cancellation` (unrecoverable `Actual Cancel` targets, >5,000 quarantine cap, or conflicting cancellation scope), `journal_lost` (missing store on an initialized entry persisted pre-fetch clamped to `MAX_TIMESTAMP`), or `malformed_store` (corrupt JSON, `.corrupt.*` backups when not already recovered, unsupported major version, outbox `>5,000`, or schema error; skips collection/writes with `degraded_until: null`; `OSError` retries via `ConfigEntryNotReady`).
- **Evidence precedence and poll-wide ambiguity:** Higher-precedence active evidence reasons (`conflicting_cancellation > malformed_cancellation > journal_lost > cancellation_evidence_overflow`) keep `degraded_reason` precedence while extending `degraded_until` to cover longer overflow horizons. Poll-wide `quarantine_ambiguous` sets `output_blocked: true` (while `evidence_degraded` stays `false`) and suspends all lineages for that poll without counting ordinary `quarantine_all` suspensions toward overflow, raising `situareness_degraded`.
- **Capacity mode (`outbox_overflow`, `evidence_degraded: false`, `output_blocked: false` unless `quarantine_ambiguous` is true, `partial: true`):** When queued plus newly planned targets exceed `5,000`, drains `100` deliverable targets first if available, queues whole plans with non-empty `new_items` atomically up to `5,000` (already-queued empty-`new_items` plans are never withheld or stripped), strips/withholds only overflowing plans (`withheld_count`), continues any remaining per-poll budget within `100` attempts/`30s`, continues bounded queued delivery under a `15`-minute `degraded_until` without freezing item age, and auto-clears once capacity fits.
- **Operator recovery (`acknowledge_degraded_at` and `.storage`):**
  - While any non-`outbox_overflow` evidence/storage degradation persists (or the same `outbox_overflow` reason persists), `degraded_at` stays at initial latch time while `degraded_until` extends.
  - Non-`malformed_store` modes clear when `degraded_until` expires on a clean poll, or on reload after setting a non-future timezone-aware ISO-8601 `acknowledge_degraded_at` in `situareness.json` with `degraded_at <= acknowledge_degraded_at <= reload time` (latched `expired_unsent` clears after seven days, or alongside active degradation / while healthy on reload only when `expired_unsent_at` is present and `expired_unsent_at <= acknowledge_degraded_at <= reload time`; when `expired_unsent_at` is missing or later, clearing active degradation leaves `expired_unsent` latched).
  - Non-string, empty, or C0/DEL/C1 control-character `acknowledge_degraded_at` values fail `situareness.json` validation (`ConfigEntryNotReady`).
  - At load time, unparseable/timezone-naive, over-length (`>100` characters), or future (`> reload time`) strings keep monitoring online, preserve `acknowledge_rejected: true` across healthy and mid-session clears, and surface reason-accurate `situareness_degraded` notices (including concurrently with `quarantine_ambiguous`); premature (`< degraded_at` or `< expired_unsent_at`), missing-anchor `expired_unsent`, `malformed_store`, or already-consumed values also reject when degraded or clearing latched `expired_unsent`. Chronological `<=100`-entry `consumed_acknowledgements` history merges across config entry data and store without loss, and triggering conditions must clear before permanent reload recovery.
  - Recover `malformed_store` only by repairing `.storage/situareness.<entry_id>`, deleting it and any `.corrupt.*` backups (or replacing its data with `{}`) and reloading (which enters `journal_lost`), or removing and re-adding the entry.
  - Resetting/replacing lost or corrupt stores or acknowledging `cancellation_evidence_overflow` early discards tombstones and can allow in-window alerts to re-evaluate or re-alert. Rely on independent official alert channels during any degraded state or after any store reset.

The integration loaded in an isolated Home Assistant 2026.11.1 test runtime; compatibility with a particular household installation and physical commissioning remain unverified.
