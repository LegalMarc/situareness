# Situareness for Home Assistant

This custom integration is uncommissioned. It independently polls NWS alerts once a minute and defaults to shadow mode. Actual installation and delivery require separate commissioning. Continue to use independent official alert channels. Provider and network delays, polling, controller outages and device behavior can delay or prevent an alert.

For a future authorized installation, copy `custom_components/situareness` from this archive to Home Assistant's `<config>/custom_components/situareness`, restart HA, then add **Situareness** under Settings > Devices & services. The optional `home-assistant/situareness.example.json` is a blank starting point for the private `<config>/situareness.json` file. Keep a local working copy under `ignored-resources/` and copy it privately to HA; reload the integration after changes. The example queries NY and DC and contains no configured footprints, rules, or recipients. Never share or commit private coordinates or device identifiers.

Configure private household longitude/latitude points under `locations`, never town centers. Optional location `name` supplies the display label and `speakers` contains HA media player entity IDs. Configure `approved_rules` as exact NWS event names mapped to reviewed starting phrases of official protective instructions. Unconfigured points, absent polygons, unmatched wording, and unapproved rules cannot produce an alarm. `phones` lists HA mobile-app service names without `notify.`; `tts_entity` identifies an HA TTS entity. Rules and targets require validation before relying on them.

Both `live_enabled` and `commissioning_passed` must be explicitly true before output services can be called. Both are false in the supplied example. Leave them false until policy replay, private footprint and source verification, coordinated phone and speaker testing, and failure/stop behavior are documented and separately authorized. These settings do not themselves prove commissioning. There is no horn, Ring, police/fire panic, recipient alert acknowledgement, or repeated-reminder adapter.

New qualifying alerts target all configured phones and speakers at affected locations only. Phone service data includes the official URL and is limited to 2,800 JSON bytes; long instructions are shortened with a prompt to open the source, and large location lists can be summarized. The full instruction remains in the private outbox. Each speaker names its own location, omits the URL, and limits spoken instructions to 300 characters with a prompt to open the source link if shortened. The budget leaves provider-envelope headroom but does not establish final APNs size or delivery.

The normative specification for CAP qualification, cancellation scoping, bounded storage, off-loop serialization, degraded states, and recovery rules is maintained in `docs/spec/o3-mvp.md` (`#home-assistant`) in the source repository.

- **Collection and delivery bounds:** Polls request NWS active GeoJSON alerts across configured states within `50s` total fetch / `25s` per-page / `50`-page / `8 MiB`-per-page limits. Delivery prioritizes new first-attempt targets ahead of up to two retries (`MAX_ATTEMPTS = 3`, `15`-minute `MAX_AGE`, `100` attempts/poll, `30`-second deadline, saved per 10-target group). Large near-capacity outboxes (up to `5,000` targets × `10 KB` instructions) serialize off Home Assistant's event loop (`serialize_in_event_loop=False`).
- **Caveats and at-least-once delivery:** An `ended_or_absent` transition does not establish official cancellation, and a crash, power loss, or save failure after Home Assistant accepts a 10-target delivery group can duplicate that group on retry. Service acceptance is not proof a person heard an alert.

## Health, storage, and degraded recovery

- **Sensor state and privacy:** `sensor.situareness_monitoring` exposes `active_count`, `event_count`, `source_feature_count`, `last_success`, `shadow`, `planned_count`, `withheld_count`, `pending_count`, `deliverable_count`, `suspended_count`, `delivery_attempts`, `delivery_failures`, `expired_unsent`, `partial`, `quarantined_count`, `quarantine_ambiguous`, `cancellation_uncertain`, `evidence_degraded`, `output_blocked`, `degraded_reason`, `degraded_at`, `degraded_until`, `acknowledge_rejected`, and up to 25 redacted `events` (`events`, `last_success`, `degraded_at`, and `degraded_until` are excluded from recorder history).
- **Private atomic storage:** State uses `Store(..., private=True, atomic_writes=True, serialize_in_event_loop=False)` (`0600` when supported), offloading setup-time validation, JSON encoding, atomic file writes, and post-fetch planning/reconciliation from HA's event loop (leaving bounded `<=10`-item group rechecks and `O(n)` in-memory bookkeeping on the loop). Poll saves verify completion via a per-save identifier (skipped during shutdown) and raise `UpdateFailed` on write failure.
- **Degraded modes and alerts:** Evidence/storage errors (`cancellation_evidence_overflow`, `malformed_cancellation`, `conflicting_cancellation`, `journal_lost`, `malformed_store`) set `evidence_degraded: true`, `output_blocked: true`, and `situareness_degraded` (`quarantine_ambiguous` sets `output_blocked: true` per poll; `outbox_overflow` withholds overflowing new plans at the `5,000`-target cap while continuing bounded delivery). All `situareness_degraded` notices indicate when live output is disabled in shadow mode.
- **Operator recovery (`acknowledge_degraded_at` and `.storage`):** Once triggers clear, non-`malformed_store` modes and latched `expired_unsent` expire after their retention windows (7 days from the latest expiration for `expired_unsent`; 15 minutes for `outbox_overflow`) or clear on reload via a valid timezone-aware non-future ISO-8601 `acknowledge_degraded_at` in `situareness.json` at or after `degraded_at` and the latest `expired_unsent_at`. Invalid/premature/reused strings set `acknowledge_rejected: true` while keeping monitoring online. Recover `malformed_store` by repairing or deleting `.storage/situareness.<entry_id>` and any `.corrupt.*` backups (or removing and re-adding the entry). Store resets or early acknowledgements discard tombstones and can re-evaluate in-window alerts; maintain independent official alert channels.

The integration loaded in an isolated Home Assistant 2026.11.1 test runtime; compatibility with a particular household installation and physical commissioning remain unverified.
