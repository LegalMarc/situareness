# O3 implementation contract

## Architecture and privacy

The Chrome extension provides a read-only room; a separately configured Home Assistant integration monitors NWS independently. Public JSON examples contain New York City and Washington, DC only. Browser settings and exports include watched locations and are sensitive. Private JSON working files belong under `ignored-resources/private-config/` and must not enter release bundles or Git history.

## Room

Collect NWS active alerts, USGS `all_hour` earthquake reports, and BBC feeds using packaged adapters. NWS and USGS target one-minute polling and BBC five-minute polling, subject to provider, network, and browser scheduling delays. USGS reports are post-event, not earthquake early warning. Display source health, times, stale and failed states, and coarse location associations without implying a household impact. Preserve bounded collections, safe links, and validation. Room settings reside in Chrome storage; a changed JSON file requires import to update that storage.

The optional `room.context_dashboard` is a non-authoritative third-party display link, initially World Monitor. It is independent of the source collectors and never authorizes an alarm. Legacy `primary_dashboard` imports remain supported. Fresh current NWS items receive retention priority within bounded history; non-expired retained items from a disabled, failed, or overdue source carry a visible cached badge (`Cached · source unavailable`), including NWS items also marked `Not in latest results` (missing or unknown NWS lifecycle defaults to cached when unavailable, whereas `expired` renders only `Source expiry passed`). All items have a seven-day collection-age bound. Global-cap history loss is disclosed separately from freshness and provider truncation, with a seven-day last-loss window and a reset when all previous source identities are removed. Disabled sources display neutral health and are excluded from enabled-source health rollups; an all-disabled collector is neutral. Startup collects overdue sources, and manual collection updates cadence. Bundled configuration failures produce an explicit room error.

## Home Assistant

This section is the normative specification for the Home Assistant integration. See [CAP source evidence and policy](../reference/cap-cancellation.md) for primary-source rationale.

### Qualification and per-feature quarantine

- Collect active NWS alerts across configured states cleanly per poll; transient HTTP, timeout, or pagination failures fail the poll without clearing prior state or latching degraded mode.
- Qualify only current `Actual` NWS `Alert`/`Update` messages issued within the 7-day `MAX_ACCEPTANCE_AGE` with valid in-range timestamps (years `2–9998` to avoid horizon overflow), complete CAP identity/reference tuples, strictly earlier referenced `sent` timestamps, `sent <= now + 5m`, valid action windows (`effective`/`onset`/`expires`/`ends`), a configured household point inside supported Polygon/MultiPolygon geometry, and an approved event and protective-instruction prefix rule.
- Reject unknown geometry, missing footprints, test messages, cancellations, and expired alerts from qualification. Only valid `Actual` `Update` and `Cancel` messages can supersede referenced predecessors; non-`Actual` (`Test`, `Exercise`, `System`) or `Alert` messages never hide or supersede referenced `Actual` alerts or migrate their pending outbox items.
- Isolate malformed, oversized, future-dated (`sent > now + 5m`), or conflicting-duplicate non-cancellation features in per-feature/per-lineage quarantine without failing unrelated valid alerts, preserving pending retries in suspension and preventing raw references from suppressing independent branches.
- When a malformed or oversized non-cancellation feature has an extractable NWS feature `id` (`https://api.weather.gov/alerts/...`), scope quarantine to `[feature_id, *absent_unreferenced_valid_refs]` (quarantining `feature_id` and absent prior records in `valid_refs` that are not referenced by another valid current candidate, even when `properties` is non-object or a reference `@id` is invalid, so unverified raw references on a non-`Cancel` feature cannot suppress a valid candidate currently present in the feed).
- Trigger poll-wide `quarantine_ambiguous: true` (suspending all lineages for that poll and raising `situareness_degraded`) only when a feature `id` cannot be safely extracted or unique quarantined IDs exceed 5,000 in one poll.
- Reconcile updates, deduplicate equivalent active lineage, persist state via private `Store(..., private=True)`, target all configured phones and only affected-location speakers, require explicit `live_enabled` and `commissioning_passed` gates (both defaulting to `false`), bridge equivalent inactive actions for at most 15 minutes, and invalidate prior pending targets on changed event or instruction.

### CAP cancellation and continuing segments

- Treat CAP references as directed evidence rather than whole-component cancellation authority. Do not infer cancellation scope from area names, VTEC equality, or overlapping UGCs.
- Keep explicitly cancelled records (including retained `state == "cancelled"` records whose `Cancel` aged out) blocked for `MAX_ACCEPTANCE_AGE` (7 days) before transitioning absent expired records to `ended_or_absent`.
- Isolate invalid or future-dated (`> +5m`) `Actual Cancel` records with recoverable targets in `uncertain_targets` without persisting raw `lineage` edges and without promoting them to authoritative cancellation when clocks advance.
- Quarantine unreferenced pre-cancellation uncertain records and suspend pending retries while current (`cancellation_uncertain`, `partial`); resolve absent uncertainty to `ended_or_absent` on clean polls (keeping existing suspended outbox items bounded by the 15-minute outbox window).
- For valid unreferenced continuing segments issued at or after a partial cancellation (`sent >= cancelled_at`), keep repeating pre-cancellation actions suspended in `quarantined` state while evaluating distinct new qualifying actions normally as `active`. Keep independent sibling branches eligible.

### Bounded storage and headroom

- Enforce caps of 1,000 stored records, 100 references per alert, 100 action fingerprints per record, 5,000 unique quarantined IDs per poll, and 5,000 outbox targets, retaining protected `Cancel`/tombstone components for 7 days from the latest component timestamp bounded at `min(timestamp, updated + 5m)` per record and clamped at `MAX_TIMESTAMP` (`9998-12-31T23:59:59+00:00`) so future-dated or far-future inputs cannot extend retention or persisted `degraded_until` past reloadable bounds.
- Because the collector accepts up to 1,000 features per poll and retained tombstones occupy protected slots, large multi-state alert bursts combined with retained tombstones can reach the 1,000-record `cancellation_evidence_overflow` bound; overflow prioritizes active/current/`Cancel`/`cancelled` records and extends `degraded_until` (clamped at `MAX_TIMESTAMP`) to the latest `dropped_horizon` across evicted protected/cancellation components (`eid in protected`, with a floor of `now + MAX_ACCEPTANCE_AGE`).
- When malformed, oversized, or conflicting `Actual Cancel` records have recoverable non-empty reference URLs within the 5,000-ID poll cap, quarantine only those targeted lineages and directed descendants (`cancellation_uncertain`, `partial`).

### Degraded states and `outbox_overflow`

- **Evidence/storage degraded modes (`evidence_degraded: true`, `output_blocked: true`):**
  - `cancellation_evidence_overflow`: Protected history exceeds 1,000 records (`degraded_until` at least 7 days and covers evicted protected/cancellation `dropped_horizon`; `withheld_count` reports qualifying plans stripped on overflow).
  - `malformed_cancellation` / `conflicting_cancellation`: An `Actual Cancel` lacks recoverable target references or exceeds the 5,000-ID quarantine cap, or conflicting cancellation evidence cannot be scoped safely (`degraded_until` at least 7 days).
  - `journal_lost`: A previously initialized config entry's store goes missing (`persisted` is `None` or `{}`). Latch with stable `degraded_at` in `journal_lost_at` across pre-fetch failures, persist before fetching, set `degraded_until >= detect_now + MAX_ACCEPTANCE_AGE` (rotating stale `journal_lost_at` past 7 days and clearing `journal_lost_at` on post-fetch saves, non-empty store loads, or `malformed_store` entry so repeat losses get a full 7-day hold).
  - `malformed_store`: Persisted JSON fails decoding (`JSONDecodeError`, `.corrupt.*` backups), major-version validation (`UnsupportedStorageVersionError`, `NotImplementedError`, `ValueError`), or deep schema validation (`bool` checks on `initialized`/`was_live`, `degraded_reason` in allowed persisted reasons, persisted outboxes `<= 5,000`); unexpected internal/runtime errors raise `ConfigEntryNotReady` for retry. Skip collection and writes to preserve disk data (`degraded_until: null`; mark `journal_initialized: true`).
- **Capacity mode (`outbox_overflow`, `evidence_degraded: false`, `output_blocked: false`, `partial: true`):**
  - When queued plus newly planned targets exceed 5,000, pre-drain one 100-target batch first if deliverable outbox items exist, then queue new whole plans atomically up to 5,000 targets and strip/withhold overflowing plans (`withheld_count`).
  - Set `degraded_reason: "outbox_overflow"` and `degraded_until = now + MAX_AGE` (15 minutes), continue bounded queued delivery (max 100 targets/poll, prioritizing first-attempt `attempts == 0` targets ahead of retries while preserving FIFO order within each tier, 30s deadline, persisting once before a 10-target group when expired items are pruned and once after each completed 10-target group, and excluding `outbox_overflow` from `last_degraded_poll` age freezing), surface active `active_count` and accurate `deliverable_count`/`suspended_count`, and clear automatically on any poll where current plans fit within 5,000. Under the 100-target/poll, 15-minute `MAX_AGE` window, overflow retries above ~1,500 targets can expire unsent.

### Recovery, notifications, and lifecycle

- Offload heavy post-fetch coordinator work (`_valid_persisted_store`, candidate/conflict resolution, `reconcile`, outbox migration and `lineage_index`, target generation, and deliverable-count qualification checks) off Home Assistant's event loop via `hass.async_add_executor_job`; async HTTP pagination and JSON payload parsing/normalization run in `collector.fetch()`.
- Surface `cancellation_uncertain` and `acknowledge_rejected` truthfully across both degraded and healthy snapshots, preserving config-level invalid/naive/over-length/future `acknowledge_rejected` state across mid-session `degraded_until` or `outbox_overflow` clears, excluding `events`, `last_success`, `degraded_at`, and `degraded_until` from recorder history, and reporting `withheld_count` alongside `planned_count`.
- Keep initial `degraded_at` stable across consecutive polls with the same active `degraded_reason` while extending `degraded_until` per poll so reload acknowledgements do not race intervening polls.
- Raise `situareness_degraded` once per `(reason, live, acknowledge_rejected)` on load and pre-fetch (qualified in shadow mode with live output disabled): name `.storage` manual repair/removal only when `degraded_reason == "malformed_store"`, name `outbox_overflow` continued delivery and plan-capacity auto-clear rules (without claiming 15-minute horizon expiry alone clears ongoing overflow), name `degraded_until` + `acknowledge_degraded_at` (>= `degraded_at`, once triggers/overflow clear) + reload for all other degraded reasons, surface rejected/re-latched acknowledgements (`acknowledge_rejected`, including healthy-state and `quarantine_ambiguous`-concurrent invalid/future `acknowledge_degraded_at` rejections). Dismiss `situareness_degraded` on recovery, unload, or before deleting the store and `.corrupt.*` backups on entry removal.
- Clear evidence/journal degradations after `degraded_until` on a clean poll once triggers clear, or via one-shot non-future `acknowledge_degraded_at` evaluated at load (`degraded_at <= acknowledge_degraded_at <= load_now`), taking permanent effect on reload only once the trigger leaves the feed. Reject only non-string, empty, or C0/DEL/C1 control-character `acknowledge_degraded_at` values in `config.validate(raw)`; at runtime coordinator load (whether degraded or healthy), reject unparseable/timezone-naive, over-length (`>100` characters), or future (`> load_now`) values, and when degraded also reject premature (`< degraded_at`), `malformed_store`, or already-consumed values (`acknowledge_rejected: true` while keeping monitoring online), persisting a bounded `consumed_acknowledgements` history (`<= 100` ISO timestamps merged across `entry.data` and store without downgrade) so stale or future configuration cannot auto-clear on later retries or unseen degradations.
- Recovering from `malformed_store` (repairing JSON, deleting store + `.corrupt.*` backups or replacing data with `{}` to enter `journal_lost`, or removing/re-adding the entry) or acknowledging `cancellation_evidence_overflow` early discards tombstones and can allow in-window alerts to re-evaluate. Pre-degradation outbox retries freeze `created` ages via `last_degraded_poll` during non-`outbox_overflow` degraded holds (up to 7+ days) so surviving active alerts resume retrying without duplication once resolved.
- Stop cancels only internal in-flight fetch tasks cleanly (`_stopped_health()` preserves non-degraded suspended counts without post-stop writes), while external cancellation of the outer refresh task propagates `asyncio.CancelledError`. No horn adapter exists; service acceptance is not proof of human receipt.
