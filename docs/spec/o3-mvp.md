# O3 implementation contract

## Architecture and privacy

The Chrome extension provides a read-only room; a separately configured Home Assistant integration monitors NWS independently. Public JSON examples contain New York City and Washington, DC only. Browser settings and exports include watched locations and are sensitive. Private JSON working files belong under `ignored-resources/private-config/` and must not enter release bundles or Git history.

## Room

Collect NWS active alerts, USGS `all_hour` earthquake reports, and BBC feeds using packaged adapters. NWS and USGS target one-minute polling and BBC five-minute polling, subject to provider, network, and browser scheduling delays. USGS reports are post-event, not earthquake early warning. Display source health, times, stale and failed states, and coarse location associations without implying a household impact. Preserve bounded collections, safe links, and validation. Room settings reside in Chrome storage; a changed JSON file requires import to update that storage.

The optional `room.context_dashboard` is a non-authoritative third-party display link, initially World Monitor. It is independent of the source collectors and never authorizes an alarm. Legacy `primary_dashboard` imports remain supported. Fresh current NWS items receive retention priority within bounded history; non-expired retained items from a disabled, failed, or overdue source carry a visible cached badge (`Cached · source unavailable`), including NWS items also marked `Not in latest results` (missing or unknown NWS lifecycle defaults to cached when unavailable, whereas `expired` renders only `Source expiry passed`). All items have a seven-day collection-age bound. Global-cap history loss is disclosed separately from freshness and provider truncation, with a seven-day last-loss window and a reset when all previous source identities are removed. Disabled sources display neutral health and are excluded from enabled-source health rollups; an all-disabled collector is neutral. Startup collects overdue sources, and manual collection updates cadence. Bundled configuration failures produce an explicit room error.

## Home Assistant

Use current actual NWS evidence issued within the seven-day maximum acceptance age (`MAX_ACCEPTANCE_AGE`) with internally consistent full CAP identity/reference tuples and strictly earlier referenced issue times, a configured household point within supported geometry, an approved event and protective-instruction rule, and a valid action window for qualification. Invalid current Alert/Update identities or reference metadata, as well as malformed, oversized, or conflicting-duplicate non-cancellation features, are quarantined per feature/lineage without failing unrelated valid alerts, preserve pending retries in suspension, and cannot establish raw grouping edges that suppress independently valid alerts or sibling branches; invalid `Actual Cancel` records isolate recoverable reference targets in `uncertain_targets` (matching exact replays via persisted identity/target keys without writing unverified references into persistent `lineage` edges). Unknown geometry, missing footprints, tests, cancellations and expired alerts cannot qualify. Reconcile updates and cancellation, deduplicate equivalent active lineage, persist pending targets, and recheck eligibility before delivery. First plans target all configured phones and only affected-location speakers. Both live and commissioning gates must be explicitly true before output calls; default to shadow. Equivalent inactive actions bridge at most 15 minutes; changed event/instruction invalidates earlier pending work. CAP references are directed message evidence; shared ancestry may group equivalent actions but never authorizes whole-component cancellation. Explicitly identified cancelled messages (including retained `state == "cancelled"` records whose original `Cancel` was evicted) remain blocked against stale replay within the seven-day horizon and transition to `ended_or_absent` once absent past that horizon. An unreferenced successor whose cancellation scope is uncertain has its pending outputs suspended and contributes partial health only while current or active; once absent and outside a partial/quarantined poll, historic uncertainty resolves to `ended_or_absent` rather than stalling unrelated monitoring. Independently supported sibling branches and continuing descendants of uncancelled branches remain eligible for their own checks and retries. Do not infer cancellation scope from area names, matching VTEC, or overlapping UGC. A later Update explicitly referencing a cancellation must independently pass qualification before it can begin a new action. Persist directed identities, references and cancellation evidence across restarts for the seven-day acceptance and cancellation-evidence horizon from the latest component timestamp, and treat missing or conflicting lineage evidence as uncertainty rather than an all-clear. Overflow prioritizes active/current/`Cancel`/`cancelled` records ahead of ordinary history and extends `degraded_until` to cover the latest `dropped_horizon` across evicted components without shrinking an earlier longer horizon. When a malformed, oversized, or conflicting `Actual` `Cancel` has recoverable non-empty target reference URLs within the poll's 5,000-identifier quarantine cap (counting unique feature and reference IDs once per poll), quarantine only those targeted lineages and their directed descendants (`cancellation_uncertain`, `partial`) without blocking independent alerts. If bounded storage overflows (`cancellation_evidence_overflow`), queued outbox targets exceed the 5,000-target bound (`outbox_overflow`, capping the persisted outbox at 5,000 while persisting reconciled records and withholding delivery), an `Actual` `Cancel` lacks recoverable target reference URLs or exceeds the 5,000-identifier quarantine cap (`malformed_cancellation`), conflicting cancellation evidence lacks recoverable target scope (`conflicting_cancellation`), a previously initialized config entry's persisted journal goes missing (`journal_lost`), or the persisted journal fails JSON/version decoding (including HA `.corrupt.*` backups; transient `OSError` raises `ConfigEntryNotReady` for retry) or fails deep schema validation including `bool` checks on `initialized` and `was_live` (`malformed_store`, marking `journal_initialized` on any non-empty or malformed store load), retain a durable degraded state with explicit `degraded_reason`, `degraded_at`, and `degraded_until` (`null` with stable `degraded_at` for `malformed_store`), raise an operator-visible Home Assistant persistent notification (`situareness_degraded`) once per degraded reason transition immediately on load and pre-fetch without re-creating on advancing timestamps (persisting `journal_lost` with stable `journal_lost_at` before fetching and keeping `journal_lost_at` on the entry through acknowledgement until the first post-recovery save completes, and dismissing `situareness_degraded` on recovery, unload, or before deleting the store on entry removal), and withhold all output until resolved (continuing read-only collection except for `malformed_store`, and excluding `degraded_at`/`degraded_until` from recorder churn). Uncorrupted degraded states clear after `degraded_until` on a clean poll or via a one-shot `acknowledge_degraded_at` evaluated solely at coordinator load/reload against load time (`degraded_at <= acknowledge_degraded_at <= load_now`), once active feed triggers (`malformed_cancellation`, `conflicting_cancellation`) or protected-record overflow (`cancellation_evidence_overflow`) are no longer present (since those ongoing triggers refresh `degraded_at` and `degraded_until` on each poll without shortening `degraded_until`); future-dated timestamps never auto-clear on later polls without a reload, and `malformed_store` persists until repaired in `.storage/situareness.<entry_id>`, replaced by deleting the store file and any `.corrupt.*` backups (or replacing its data with empty JSON `{}`) on disk (which transitions to `journal_lost`), or cleared by removing and re-adding the integration entry. Resetting or replacing a corrupt or lost store (`malformed_store` / `journal_lost`), removing/re-adding the entry, or acknowledging `cancellation_evidence_overflow` early, discards or truncates historical tombstones and may allow previously seen or cancelled alerts still in their acceptance window to re-evaluate or re-alert. Alerts that first qualify while output is degraded, as well as undelivered pre-degradation outbox targets whose retry budget was blocked by degradation (preserving `last_degraded_poll` until post-recovery outbox migration), are evaluated for delivery once degradation resolves without duplicating pre-degradation deliveries. See [CAP source evidence and policy](../reference/cap-cancellation.md). Ambiguous quarantine (unextractable IDs or >5,000 unique quarantined identifiers per poll) suspends all lineages for that poll. Unload cancels in-flight fetches on stop (returning non-degraded stopped health with queued targets accounted as suspended when healthy) and stops later saves; entry removal dismisses `situareness_degraded` before deleting the private journal and any `.corrupt.*` backups. No horn adapter is implemented. Do not equate service acceptance with human receipt.

## Research and verification

`config/source-catalog.example.json` is a research catalog and is not consumed at runtime. The source skill can maintain a local catalog and propose supported room changes with validation; additional sources need adapters. Run offline checks, isolated browser tests and isolated actual Home Assistant tests as appropriate. Record exact results, dependencies, warnings, and untested physical behavior. Live commissioning is separate.
