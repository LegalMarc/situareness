# O3 implementation contract

## Architecture and privacy

The Chrome extension provides a read-only room; a separately configured Home Assistant integration monitors NWS independently. Public JSON examples contain New York City and Washington, DC only. Browser settings and exports include watched locations and are sensitive. Private JSON working files belong under `ignored-resources/private-config/` and must not enter release bundles or Git history.

## Room

Collect NWS active alerts, USGS `all_hour` earthquake reports, and BBC feeds using packaged adapters. NWS and USGS target one-minute polling and BBC five-minute polling, subject to provider, network, and browser scheduling delays. USGS reports are post-event, not earthquake early warning. Display source health, times, stale and failed states, and coarse location associations without implying a household impact. Preserve bounded collections, safe links, and validation. Room settings reside in Chrome storage; a changed JSON file requires import to update that storage.

The optional `room.context_dashboard` is a non-authoritative third-party display link, initially World Monitor. It is independent of the source collectors and never authorizes an alarm. Legacy `primary_dashboard` imports remain supported. Fresh current NWS items receive retention priority within bounded history; disabled, failed or overdue source data is visibly cached. All items have a seven-day collection-age bound. Global-cap history loss is disclosed separately from freshness and provider truncation, with a seven-day last-loss window and a reset when all previous source identities are removed. Disabled sources display neutral health and are excluded from enabled-source health rollups; an all-disabled collector is neutral. Startup collects overdue sources, and manual collection updates cadence. Bundled configuration failures produce an explicit room error.

## Home Assistant

Use current actual NWS evidence issued within the seven-day maximum acceptance age (`MAX_ACCEPTANCE_AGE`) with internally consistent full CAP identity/reference tuples and strictly earlier referenced issue times, a configured household point within supported geometry, an approved event and protective-instruction rule, and a valid action window for qualification. Invalid current Alert/Update identities or reference metadata, as well as malformed or oversized non-cancellation features, are quarantined per feature/lineage without failing unrelated valid alerts, preserve pending retries in suspension, and cannot establish edges that suppress independently valid alerts. Unknown geometry, missing footprints, tests, cancellations and expired alerts cannot qualify. Reconcile updates and cancellation, deduplicate equivalent active lineage, persist pending targets, and recheck eligibility before delivery. First plans target all configured phones and only affected-location speakers. Both live and commissioning gates must be explicitly true before output calls; default to shadow. Equivalent inactive actions bridge at most 15 minutes; changed event/instruction invalidates earlier pending work. CAP references are directed message evidence; shared ancestry may group equivalent actions but never authorizes whole-component cancellation. Explicitly identified cancelled messages remain blocked against stale replay. An unreferenced successor whose cancellation scope is uncertain has its pending outputs suspended and contributes partial health only while current or active; once absent and outside a partial/quarantined poll, historic uncertainty resolves to `ended_or_absent` rather than stalling unrelated monitoring. Independently supported sibling branches and continuing descendants of uncancelled branches remain eligible for their own checks and retries. Do not infer cancellation scope from area names, matching VTEC, or overlapping UGC. A later Update explicitly referencing a cancellation must independently pass qualification before it can begin a new action. Persist directed identities, references and cancellation evidence across restarts for the seven-day acceptance and cancellation-evidence horizon from the latest component timestamp, and treat missing or conflicting lineage evidence as uncertainty rather than an all-clear. If bounded storage overflows (`cancellation_evidence_overflow`), an `Actual` `Cancel` fails normalization or has no recoverable target reference URLs (`malformed_cancellation`), conflicting cancellation evidence arrives (`conflicting_cancellation`), or the persisted journal fails deep schema validation (`malformed_store`), retain a durable degraded state with explicit `degraded_reason`, `degraded_at`, and `degraded_until` and withhold all output until resolved (continuing read-only collection except for `malformed_store`). Uncorrupted degraded states clear after the seven-day acceptance window (`degraded_until`) on a clean poll or via a one-shot non-future `acknowledge_degraded_at` at or after the latest `degraded_at`, once the triggering condition is no longer present in the feed or overflowing protected bounds (since an active trigger refreshes `degraded_at` and `degraded_until` on each poll); `malformed_store` persists until the corrupt store is repaired or replaced. Alerts that first qualify while output is degraded, as well as undelivered pre-degradation outbox targets whose retry budget was blocked by degradation, are evaluated for delivery once degradation resolves without duplicating pre-degradation deliveries. See [CAP source evidence and policy](../reference/cap-cancellation.md). Oversized or malformed non-cancellation lineages are quarantined with partial health while unrelated verified alerts continue; ambiguous quarantine suspends all lineages for that poll. Entry removal stops later saves before deleting the private journal. No horn adapter is implemented. Do not equate service acceptance with human receipt.

## Research and verification

`config/source-catalog.example.json` is a research catalog and is not consumed at runtime. The source skill can maintain a local catalog and propose supported room changes with validation; additional sources need adapters. Run offline checks, isolated browser tests and isolated actual Home Assistant tests as appropriate. Record exact results, dependencies, warnings, and untested physical behavior. Live commissioning is separate.
