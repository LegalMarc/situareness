# Home Assistant integration

This integration is an uncommissioned implementation. It runs independently of Chrome, requests NWS active GeoJSON alerts for the configured states every minute in one combined query, and defaults to shadow mode. It does not cover non-weather sources. The isolated tests use simulated services and locations; actual installation and delivery require separate commissioning.

## Setup for a future authorized installation

Copy `custom_components/situareness` into Home Assistant's `<config>/custom_components/situareness`, restart Home Assistant, then use Settings > Devices & services > Add integration > Situareness. A first-ever successful poll in shadow mode establishes the initial baseline. On later restarts, new current qualifying alerts are considered normally. Enabling both live gates reevaluates currently qualifying alerts, including alerts previously seen in shadow. Continue to use independent official alert channels.

The integration optionally reads `<config>/situareness.json` at setup. If absent it queries the sample states NY and DC with no locations, approved rules, or recipients. Change `states` for the areas being monitored. Use `home-assistant/situareness.example.json` as a starting point, store a local working copy under the git-ignored `ignored-resources/` directory, copy it privately to `<config>/situareness.json` on HA, and reload the integration after changes. Never commit precise household coordinates or device details. A malformed file fails setup instead of enabling defaults silently. Placeholders contain no household coordinates. A location's optional `point` is a GeoJSON longitude, latitude pair for the private household, not a town center. An optional `name` supplies the affected-location label included in phone and speaker messages; it defaults to the location ID. Do not use a private address as a display name. `speakers` is an optional list of HA `media_player` entity IDs. Only point footprints and Polygon/MultiPolygon geometries are supported. Missing geometry, zone-only alerts, unknown footprints, unsupported antimeridian polygons, and county or town matches cannot qualify.

`approved_rules` maps an exact NWS event name to a list of exact case-insensitive **starting phrases** of official protective instructions, each at least 10 characters. For example, an administrator could use `{"Tornado Warning": ["Take shelter immediately"]}` only after validating that wording and its consequences against actual official messages. No rule is preapproved. The instruction must begin with a configured phrase, so wording changes can suppress a valid warning. This is a conservative string match, not semantic verification or a substitute for rule review. A consistent full CAP identity tuple, matching reference tuples with strictly earlier issue times, Actual status and Alert/Update message type, Immediate/Expected urgency, Observed/Likely certainty, valid times, an issue time (`sent`) within the seven-day maximum acceptance age (`MAX_ACCEPTANCE_AGE`), effective now, onset within six hours, an unexpired action period, and a matching private footprint are also required. Invalid current identity or reference metadata is quarantined per feature/lineage before planning, and its references cannot suppress independently valid candidates. Within the seven-day acceptance window, a message can remain actionable more than an hour after issuance; successful retrieval from the active feed and its current time windows govern freshness.

`phones` contains HA mobile-app notification service names without the `notify.` prefix, such as `mobile_app_example`. `tts_entity` is an HA `tts` entity ID. Plans target all configured phone services and speakers only for matching locations. Phone delivery uses the Companion app critical notification payload, subject to phone permissions and platform support. Speaker delivery uses `tts.speak`. Phone service data is limited to 2,800 bytes as JSON with conservative escaping, including its title, message, and source URL. Long instructions are shortened with a prompt to open the source; the full instruction remains in the private outbox. Large location lists may be summarized. Each speaker message names its own affected location, omits the URL, and limits spoken instructions to 300 characters; when shortened, it directs listeners to the source link in the phone alert. This local service-data budget leaves provider-envelope headroom but does not prove the final APNs payload size or delivery. API acceptance is not evidence that someone heard an alert. Each output is attempted independently. There are no horn, Ring, police/fire panic, acknowledgement, repeat, or escalation adapters.

Two separately explicit booleans, `live_enabled` and `commissioning_passed`, must both be `true` for either output adapter to call HA services. Both are `false` in the example. Do not set either gate until a separate authorized commissioning process has passed: replay policy cases, verify exact locations and rules, test the actual phone and speaker paths with household coordination, document failure/stop behavior, and confirm independent alert sources. These booleans record administrator intent; the code cannot verify that commissioning actually occurred. Changing either requires an integration reload.

## Health, reconciliation and limits

The `sensor.situareness_monitoring` entity reports qualifying active count, last successful collection time, shadow status, planned and attempted counts, degraded status (`degraded_reason`, `degraded_at`), and at most 25 redacted event summaries. Entity ID may vary. No household coordinates, device names, or instructions are included in its attributes. HA entity attributes are visible to users and integrations with access to HA state; they are not a public API or a substitute for an authenticated bridge. On source failure (including transient HTTP, timeout, or pagination failures after seeing a Cancel) the coordinator is unavailable and retains its last successful data rather than announcing an empty feed or latching degraded state. The combined configured-state request must succeed before incident reconciliation; pagination, response size and count are bounded, and request or envelope failures fail the poll. Individual malformed or oversized features inside a valid `FeatureCollection` are quarantined per feature/lineage rather than failing the whole poll.

The persisted journal records incident fingerprints, decision reasons and affected location IDs. Its per-target outbox also contains alert text and device targets and must remain private.

A complete poll marks a missing prior active alert `ended_or_absent`, which does not establish an official cancellation. NWS updates reconcile the known lineage, including root-only references. Equivalent active actions are deduplicated; inactive action history is retained for at most 15 minutes to bridge temporary absence or ineligibility. A changed event or instruction invalidates the earlier pending action. A changed protective instruction, event, urgency, certainty, or affected household can create a new plan. An expiration-only or end-time-only update refreshes eligibility without sending another alarm; a future policy may distinguish extensions that warrant communication.

Before sending, each target is persisted in an outbox. An unsuccessful service call is retried on a later complete poll, at most three attempts and within 15 minutes of queuing. Pending work is suspended during a temporary absence or ineligible update and can resume only when a current equivalent alert qualifies again; it is discarded at an actual cancellation boundary, when the action changes, the target is removed, live mode is disabled, or retry limits expire. On restart pending work is rechecked against the current feed. A crash after a service accepts a call but before that acceptance is saved can cause a duplicate. Each poll starts at most 100 target attempts and starts no new group after 30 seconds; each group rechecks the current clock, alert action window and pending age. Remaining work stays queued for the next complete poll.

A cancellation is evidence about the CAP message identities it explicitly references. An exact referenced message is blocked on replay; a known unreferenced pre-cancellation successor whose relationship or scope is uncertain is quarantined, and its retry is suspended, while valid continuing segments issued at or after a partial cancellation qualify normally for new actions (`state == "active"`) and keep pre-cancellation pending actions suspended. Historic cancellation uncertainty clears to `ended_or_absent` once the uncertain record and cancellation leave the feed (and no poll-wide partial ambiguity remains), rather than stalling unrelated monitoring; any remaining suspended outbox retry stays suspended (and can migrate only to an equivalent active update) until invalidated by a changed action or expired under the 15-minute outbox limit. An independently supported sibling branch can still qualify and follow its own updates. A later qualifying update that explicitly references a valid earlier cancellation can establish a new action, even when it also references older messages. CAP tuple conflicts, incomplete history and legacy journals can leave a related component uncertain. The source does not establish a household all-clear, and a cancellation issued between polls is not immediately known. See [CAP cancellation evidence](../reference/cap-cancellation.md) for the source and limits.

The journal is bounded to 1,000 records, each alert to 100 references, and each merged record to 100 current action fingerprints. Current source records, `Cancel` tombstones, and active `cancelled` records within the seven-day acceptance and cancellation-evidence horizon (measured from the latest `ends`, `expires`, `sent`, or referenced timestamp in the component, falling back to `updated` only if a record has none) are retained ahead of ordinary history. Once a cancellation component is past that seven-day horizon and no member appears in the current feed, its tombstone protection is cleared and its `cancelled` records transition to `ended_or_absent` so it ages out normally under the 1,000-record cap. Malformed, oversized, or conflicting duplicate non-`Cancel` features with an extractable `feature_id` quarantine scoped to `[feature_id, *valid_refs]` while unrelated alerts and independently supported siblings continue; per-event quarantine does not turn unrelated absent active alerts into `unconfirmed`. The sensor reports `source_feature_count`, `event_count`, `partial`, `quarantined_count`, `quarantine_ambiguous` and `cancellation_uncertain`. Only poll-wide partial ambiguity (`quarantine_ambiguous` or partial without scoped lineages) preserves missing prior incidents as `unconfirmed` rather than treating them as ended. Up to 5,000 unique identifiers (counting both feature IDs and reference IDs, including conflicting duplicates) from quarantined features are retained per poll; `quarantine_ambiguous` is set (raising `situareness_degraded` for that poll and suspending all current and absent lineages) only when a feature `id` cannot be extracted or the 5,000-ID quarantine cap is exceeded (while malformed/oversized `Actual` `Cancel` features lacking valid targets or exceeding the cap latch `malformed_cancellation`, and conflicting cancellation evidence lacking recoverable targets or exceeding the cap latches `conflicting_cancellation`). Invalid response envelopes and pagination failures fail the poll.

If current records and active cancellation history exceed the 1,000-record journal limit (`cancellation_evidence_overflow`, prioritizing active/current/`Cancel`/`cancelled` records and setting `degraded_until` to cover the latest `dropped_horizon` across evicted components without shrinking an earlier longer horizon), queued outbox targets exceed the 5,000-target bound (`outbox_overflow`, capping the persisted outbox at 5,000 targets while blocking delivery), an `Actual` `Cancel` lacks recoverable target references or exceeds the 5,000-identifier quarantine cap (`malformed_cancellation`), unrecoverable conflicting cancellation evidence arrives (`conflicting_cancellation`), or a previously initialized config entry's persisted store goes missing (`journal_lost`, stabilizing `degraded_at` in `journal_lost_at`, persisting before the next fetch, and surviving an unavailable feed), the integration persists a durable degraded state (`evidence_degraded: true`, `output_blocked: true`, `degraded_reason`, `degraded_at`, `degraded_until`), creates a Home Assistant persistent notification (`situareness_degraded`, dismissed on recovery, unload, or entry removal), and sets `active_count` to unknown while continuing read-only collection (without marking withheld plans as delivered or burning outbox retry age on active pre-degradation targets) and reporting collected `event_count`, `source_feature_count`, and redacted `events`. A deep-validated malformed or unparseable/corrupt JSON persisted store (`malformed_store`, including HA's `.corrupt.*` backup files and setting `journal_initialized: true` on any non-empty or malformed store load) also enters degraded state (persisting a stable `degraded_at` via `malformed_store_at` in entry data and `degraded_until: null`) and skips collection so the corrupt disk store is not overwritten, reporting `partial: false`, `quarantine_ambiguous: false`, and `cancellation_uncertain: false`. While an active feed trigger (`malformed_cancellation`, `conflicting_cancellation`) or >1,000-record capacity overflow (`cancellation_evidence_overflow`) remains present, each poll refreshes `degraded_at` and `degraded_until`, so `acknowledge_degraded_at` and the seven-day horizon clear degradation only after the triggering condition is no longer present (or protected history drops within bounds); `outbox_overflow` caps the persisted outbox at 5,000 targets when triggered and recovers after `degraded_until` expires or load-time `acknowledge_degraded_at` clears it (re-triggering only if post-recovery plans again push the outbox above 5,000). Once clear of new triggers, uncorrupted degraded states recover automatically after `degraded_until` (dismissing `situareness_degraded`), or sooner when an administrator explicitly sets a one-shot `acknowledge_degraded_at` in `situareness.json` and reloads/restarts the integration; `acknowledge_degraded_at` is evaluated **only at coordinator load/reload** against load time (`degraded_at <= acknowledge_degraded_at <= load_now`), so a future-dated timestamp does not auto-clear on later polls without a reload. A `malformed_store` cannot be cleared by `acknowledge_degraded_at` and requires either repairing the persisted store JSON on disk and reloading, deleting the store file (and any `.corrupt.*` backup files) on disk (or replacing its data with empty JSON `{}`) and reloading (which transitions to `journal_lost`), or removing and re-adding the integration entry (which deletes the corrupt store and backups and dismisses `situareness_degraded`). Resetting or replacing a corrupt or lost store (`malformed_store` / `journal_lost`), or acknowledging `cancellation_evidence_overflow` early, discards or truncates historical tombstones and may allow previously seen or cancelled alerts still in their acceptance window to re-evaluate or re-alert. Continue to use independent official alert channels while degraded. A persistence failure can prevent the degraded state itself from being saved; the poll fails and no output is started in that case.

The outbox is bounded to 5,000 targets; exceeding 5,000 targets caps the outbox at 5,000 items and enters `outbox_overflow` degraded state rather than crashing collection. Private state is persisted using Home Assistant's `Store(..., private=True)` (`0600` permissions when supported by HA storage); removing the integration entry deletes its private journal, outbox store, and any `.corrupt.*` backups, while the separately managed configuration file remains.

The sensor reports `pending_count` as all queued items, with `deliverable_count` currently eligible and `suspended_count` the remainder. The sensor excludes `events`, `last_success`, `degraded_at`, and `degraded_until` from recorder history while retaining them in current state. These are retries of failed or uncertain calls, not repeated reminders. A failure of any source request blocks that poll, and while degraded states create the `situareness_degraded` HA persistent notification, ordinary transient fetch failures do not send external notifications.

## Verification and references

Run `python3 -m unittest discover -s tests/ha -v` for standard-library policy, mock transport, and mocked service-boundary tests. These do not exercise an installed HA instance, HA entity registration, the actual companion app, or speakers. Read-only live NWS samples were separately checked during development. Home Assistant APIs were checked against official [config entries](https://developers.home-assistant.io/docs/config_entries_index/), [config flows](https://developers.home-assistant.io/docs/config_entries_config_flow_handler/), [data fetching](https://developers.home-assistant.io/docs/integration_fetching_data/), and [sensor entity](https://developers.home-assistant.io/docs/core/entity/sensor/) documentation. The [NWS API](https://www.weather.gov/documentation/services-web-api) documents active state alerts and its GeoJSON API. The isolated test below exercises the pinned HA version and interfaces; compatibility with a particular household installation, physical delivery, and commissioning remain unverified.

Delivery interfaces follow the official [Companion critical notification documentation](https://companion.home-assistant.io/docs/notifications/critical-notifications/) and [HA TTS speak action](https://www.home-assistant.io/actions/tts.speak/).

## Local Home Assistant runtime test

The optional `tests/ha/real` suite was run against Home Assistant **2026.11.1**, pytest-homeassistant **2026.11.1**, and Python **3.14.6**, installed only in `work/ha-venv`. It uses the real HA config flow, custom-integration loader, entity registry, coordinator, disk-backed Store and service registry. NWS data and service targets are simulated locally. Ten tests passed, including a qualified alert through a registered fake notify service, invalid-identity quarantine with an independent valid alert, a separate shadow-mode no-output check, actual recorder database exclusions, removal during an in-flight refresh, degraded-mode collection with output blocked and `acknowledge_degraded_at` recovery, `journal_lost` detection when a persisted store disappears, `journal_lost` persistence and notification dismissal when a reload fails before first fetch and the entry is removed, and corrupt JSON store loading entering `malformed_store`; they do not test the household HA installation, real network collection through HA, or physical delivery. HA's test dependency stack emitted five upstream deprecation warnings from `homeassistant.components.http` and `backoff`; they were not suppressed or fixed in this project.

To reproduce in an isolated Python 3.14 environment, run:

```sh
uv venv work/ha-venv --python python3.14
uv pip install --python work/ha-venv/bin/python 'homeassistant==2026.11.1' 'pytest-homeassistant==2026.11.1'
npm run test:ha:real
```

The manifest links to this integration documentation.

The one-minute interval is a polling target, not a real-time or delivery guarantee. Provider propagation and caching, network failures, polling duration, HA availability and device behavior add delay. Maintain independent official alert channels. NWS's [OpenAPI specification](https://api.weather.gov/openapi.json) defines `area` as a comma-separated array; the `area` parameter accepts a comma-separated list of areas.
