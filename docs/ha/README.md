# Home Assistant integration

This integration is an uncommissioned implementation. It runs independently of Chrome, requests NWS active GeoJSON alerts for the configured states every minute in one combined query, and defaults to shadow mode. It does not cover non-weather sources. The isolated tests use simulated services and locations; actual installation and delivery require separate commissioning.

## Setup for a future authorized installation

Copy `custom_components/situareness` into Home Assistant's `<config>/custom_components/situareness`, restart Home Assistant, then use Settings > Devices & services > Add integration > Situareness. A first-ever successful poll in shadow mode establishes the initial baseline. On later restarts, new current qualifying alerts are considered normally. Enabling both live gates reevaluates currently qualifying alerts, including alerts previously seen in shadow. Continue to use independent official alert channels.

The integration optionally reads `<config>/situareness.json` at setup. If absent it queries the sample states NY and DC with no locations, approved rules, or recipients. Change `states` for the areas being monitored. Use `home-assistant/situareness.example.json` as a starting point, store a local working copy under the git-ignored `ignored-resources/` directory, copy it privately to `<config>/situareness.json` on HA, and reload the integration after changes. Never commit precise household coordinates or device details. A malformed file fails setup instead of enabling defaults silently. Placeholders contain no household coordinates. A location's optional `point` is a GeoJSON longitude, latitude pair for the private household, not a town center. An optional `name` supplies the affected-location label included in phone and speaker messages; it defaults to the location ID. Do not use a private address as a display name. `speakers` is an optional list of HA `media_player` entity IDs. Only point footprints and Polygon/MultiPolygon geometries are supported. Missing geometry, zone-only alerts, unknown footprints, unsupported antimeridian polygons, and county or town matches cannot qualify.

`approved_rules` maps an exact NWS event name to a list of exact case-insensitive **starting phrases** of official protective instructions, each at least 10 characters. For example, an administrator could use `{"Tornado Warning": ["Take shelter immediately"]}` only after validating that wording and its consequences against actual official messages. No rule is preapproved. The instruction must begin with a configured phrase, so wording changes can suppress a valid warning. This is a conservative string match, not semantic verification or a substitute for rule review. A consistent full CAP identity tuple, matching reference tuples with strictly earlier issue times, Actual status and Alert/Update message type, Immediate/Expected urgency, Observed/Likely certainty, valid times, an issue time (`sent`) within the seven-day maximum acceptance age (`MAX_ACCEPTANCE_AGE`), effective now, onset within six hours, an unexpired action period, and a matching private footprint are also required. Invalid current identity or reference metadata is quarantined per feature/lineage before planning, and its references cannot suppress independently valid candidates. Within the seven-day acceptance window, a message can remain actionable more than an hour after issuance; successful retrieval from the active feed and its current time windows govern freshness.

`phones` contains HA mobile-app notification service names without the `notify.` prefix, such as `mobile_app_example`. `tts_entity` is an HA `tts` entity ID. Plans target all configured phone services and speakers only for matching locations. Phone delivery uses the Companion app critical notification payload, subject to phone permissions and platform support. Speaker delivery uses `tts.speak`. Phone service data is limited to 2,800 bytes as JSON with conservative escaping, including its title, message, and source URL. Long instructions are shortened with a prompt to open the source; the full instruction remains in the private outbox. Large location lists may be summarized. Each speaker message names its own affected location, omits the URL, and limits spoken instructions to 300 characters; when shortened, it directs listeners to the source link in the phone alert. This local service-data budget leaves provider-envelope headroom but does not prove the final APNs payload size or delivery. API acceptance is not evidence that someone heard an alert. Each output is attempted independently. There are no horn, Ring, police/fire panic, recipient alert acknowledgement, repeat, or escalation adapters.

Two separately explicit booleans, `live_enabled` and `commissioning_passed`, must both be `true` for either output adapter to call HA services. Both are `false` in the example. Do not set either gate until a separate authorized commissioning process has passed: replay policy cases, verify exact locations and rules, test the actual phone and speaker paths with household coordination, document failure/stop behavior, and confirm independent alert sources. These booleans record administrator intent; the code cannot verify that commissioning actually occurred. Changing either requires an integration reload.

## Health, reconciliation and limits

The normative specification for qualification, CAP cancellation scope, bounded storage, and degraded-mode recovery is in [the O3 Home Assistant contract](../spec/o3-mvp.md#home-assistant) and [CAP cancellation evidence](../reference/cap-cancellation.md). For operators:

- **Sensor state and attributes:** `sensor.situareness_monitoring` exposes `active_count`, `event_count`, `source_feature_count`, `last_success`, `shadow`, `planned_count`, `withheld_count`, `pending_count`, `deliverable_count`, `suspended_count`, `delivery_attempts`, `delivery_failures`, `expired_unsent`, `partial`, `quarantined_count`, `quarantine_ambiguous`, `cancellation_uncertain`, `evidence_degraded`, `output_blocked`, `degraded_reason`, `degraded_at`, `degraded_until`, `acknowledge_rejected`, and up to 25 redacted `events` (no coordinates, devices, or instructions). `events`, `last_success`, `degraded_at`, and `degraded_until` are excluded from recorder history.
- **Collection, bounds, and throughput:**
  - Combined state polls fail cleanly on HTTP, timeout (`50s` total fetch / `25s` per page), response-size (`8 MiB`/page), or pagination (`50` pages) errors without clearing prior state, deduplicating identical feature copies and accepting >1,000-feature bursts.
  - Event-loop responsiveness: HTTP pagination runs asynchronously, per-page JSON decoding and feature normalization/quarantine run in worker threads, and post-fetch persistence validation, reconciliation, planning, deliverable counting, and batch selection run on Home Assistant's executor; only per-group `<=10`-item qualification rechecks run on the event loop between group saves.
  - Retained storage caps: `1,000` records, `100` references/alert, `100` fingerprints/record, `5,000` unique quarantined IDs/poll, and `5,000` outbox targets under a 7-day acceptance horizon (`MAX_ACCEPTANCE_AGE`, observation-bounded at `updated + 5m` and clamped at `MAX_TIMESTAMP`).
  - Bounded history protects cancellation components, `active`, `cancelled`, cancellation-lineage, `prior_state == "active"`, `<=15m` bridge-window actions, and scoped quarantined lineages even when absent; it excludes poll-wide `quarantine_all` / `unconfirmed` suspensions lacking active prior state or `<=15m` actions, ordinary `ineligible` items, and non-actionable hidden `superseded` placeholders (truncating >1,000-feature ambiguous bursts cleanly without false overflow, with safe snapshot fallback for evicted `ineligible` items). An `ended_or_absent` transition does not establish an official cancellation.
  - Deliveries attempt up to three total attempts (`MAX_ATTEMPTS = 3`: one initial call plus up to two retries for failed/uncertain calls, not repeated reminders) within 15 minutes (`MAX_AGE`), prioritizing first attempts (`attempts == 0`) ahead of retries (`100` targets/poll, `30s` deadline, coalesced to at most one store save per 10-target group).
  - Outbox items store up to 10KB instructions, so large near-capacity outboxes serialize tens of MB per group save. If near-capacity pre-drain exhausts the `100`-attempt or `30s` budget, newly queued plans wait until the next poll; a crash or post-group save failure after Home Assistant accepts a 10-target delivery group can duplicate that group on retry.
  - Unexhausted queued targets for an active (or suspended-from-active) alert expiring via 15-minute `MAX_AGE`, backward clock rollback (`created > now`), or target removal from `situareness.json`, plus active-alert targets exhausting all three delivery attempts, increment `expired_unsent`, record `expired_unsent_reasons`, set `partial: true` and expired outcomes, and latch `situareness_degraded` for 7 days (resetting elapsed expiration counts once the 7-day window passes) or until acknowledged on reload. Non-`outbox_overflow` degraded holds freeze item age via `last_degraded_poll`.
- **Private storage, degraded recovery, and shutdown:**
  - State uses Home Assistant `Store(..., private=True)` and validates every record `state` and non-`null` `prior_state` (`{active, ineligible, ended_or_absent, quarantined, unconfirmed, superseded, cancelled}`), `save_id`, and `expired_unsent_reasons` / outcome `"reason"` values (`{age, clock_rollback, target_removed, exhausted}`). Schema, JSON, or version errors latch `malformed_store` (preserving disk data), transient storage `OSError`/internal errors raise `ConfigEntryNotReady`, and missing stores on initialized entries latch `journal_lost` clamped at `MAX_TIMESTAMP`.
  - When Home Assistant is not stopping, each persisted store save verifies its `save_id` on disk so swallowed storage write failures raise `UpdateFailed` before updating post-save memory (`expired_unsent*`, `last_degraded_poll`); shutdown-deferred saves skip verification so final writes are not treated as failed polls.
  - Evidence/storage degradations (`cancellation_evidence_overflow`, `malformed_cancellation`, `conflicting_cancellation`, `journal_lost`, `malformed_store`) block output and raise `situareness_degraded`; higher-precedence active evidence reasons (`conflicting_cancellation > malformed_cancellation > journal_lost > cancellation_evidence_overflow`) keep `degraded_reason` precedence over lower-precedence concurrent triggers while extending `degraded_until` to cover any longer overflow horizon. `outbox_overflow` withholds only overflowing non-empty new plans under a 15-minute horizon while continuing bounded queued delivery until capacity clears.
  - Across consecutive evidence/storage or identical `outbox_overflow` polls, `degraded_at` stays fixed while `degraded_until` extends. One-shot timezone-aware non-future `acknowledge_degraded_at` clears active degradation on reload once triggers leave when `degraded_at <= acknowledge_degraded_at <= reload time`, and clears `expired_unsent` on reload only when `expired_unsent_at` is present and `expired_unsent_at <= acknowledge_degraded_at <= reload time` (otherwise leaving `expired_unsent` latched).
  - Invalid, timezone-naive, over-length (`>100`), or future `acknowledge_degraded_at` strings keep monitoring online, preserve `acknowledge_rejected: true` across healthy and mid-session clears, and surface reason-accurate notices (including concurrently with `quarantine_ambiguous`); premature, `malformed_store`, or already-consumed values also reject when degraded or clearing latched `expired_unsent`. Chronological `<=100`-entry `consumed_acknowledgements` history merges across config entry data and store without loss; non-string, empty, or C0/DEL/C1 control-character values fail config validation.
  - Recover `malformed_store` by repairing or deleting the store and `.corrupt.*` backups (or replacing store data with `{}`) in `.storage` or removing/re-adding the entry; the first post-recovery save deletes stale `.corrupt.*` backups (logging warnings and retrying later if unlink fails). Unloading stops the coordinator before unloading platforms (resuming polling and notification sync, including `quarantine_ambiguous`, if platform unload fails), aborts post-fetch saves/delivery once stopping, and dismisses `situareness_degraded` on failed platform forwarding, abandoned/failed initial setup retries, unload, or removal. Store resets or early acknowledgements discard tombstones and may allow in-window alerts to re-evaluate.

## Verification and references

Run `python3 -m unittest discover -s tests/ha -v` for standard-library policy, mock transport, and mocked service-boundary tests. These do not exercise an installed HA instance, HA entity registration, the actual companion app, or speakers. Read-only live NWS samples were separately checked during development. Home Assistant APIs were checked against official [config entries](https://developers.home-assistant.io/docs/config_entries_index/), [config flows](https://developers.home-assistant.io/docs/config_entries_config_flow_handler/), [data fetching](https://developers.home-assistant.io/docs/integration_fetching_data/), and [sensor entity](https://developers.home-assistant.io/docs/core/entity/sensor/) documentation. The [NWS API](https://www.weather.gov/documentation/services-web-api) documents active state alerts and its GeoJSON API. The isolated test below exercises the pinned HA version and interfaces; compatibility with a particular household installation, physical delivery, and commissioning remain unverified.

Delivery interfaces follow the official [Companion critical notification documentation](https://companion.home-assistant.io/docs/notifications/critical-notifications/) and [HA TTS speak action](https://www.home-assistant.io/actions/tts.speak/).

## Local Home Assistant runtime test

The optional `tests/ha/real` suite was run against Home Assistant **2026.11.1**, pytest-homeassistant **2026.11.1**, and Python **3.14.6**, installed only in `work/ha-venv`. It uses the real HA config flow, custom-integration loader, entity registry, coordinator, disk-backed Store and service registry. NWS data and service targets are simulated locally. Thirteen tests passed, including a qualified alert through a registered fake notify service, invalid-identity quarantine with an independent valid alert, a separate shadow-mode no-output check, actual recorder database exclusions, removal during an in-flight refresh, degraded-mode collection with output blocked and `acknowledge_degraded_at` recovery, `journal_lost` detection when a persisted store disappears, `journal_lost` persistence and notification dismissal when a reload fails before first fetch and the entry is removed, abandoned `SETUP_RETRY` unload dismissing `situareness_degraded`, read-only `.storage` save verification failing the poll before delivery despite HA `Store` error logging, corrupt JSON store loading entering `malformed_store`, and unsupported store major version mismatches preserving disk state under `malformed_store`; they do not test the household HA installation, real network collection through HA, or physical delivery. HA's test dependency stack emitted five upstream deprecation warnings from `homeassistant.components.http` and `backoff`; they were not suppressed or fixed in this project.

To reproduce in an isolated Python 3.14 environment, run:

```sh
uv venv work/ha-venv --python python3.14
uv pip install --python work/ha-venv/bin/python 'homeassistant==2026.11.1' 'pytest-homeassistant==2026.11.1'
npm run test:ha:real
```

The manifest links to this integration documentation.

The one-minute interval is a polling target, not a real-time or delivery guarantee. Provider propagation and caching, network failures, polling duration, HA availability and device behavior add delay. Maintain independent official alert channels. NWS's [OpenAPI specification](https://api.weather.gov/openapi.json) defines `area` as a comma-separated array; the `area` parameter accepts a comma-separated list of areas.
