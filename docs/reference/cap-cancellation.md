# CAP references and NWS cancellation scope

Verified against the linked public sources on November 16–17, 2026. This note describes source evidence and a conservative implementation policy; it is not proof that the present integration implements the policy or that any household delivery has been commissioned.

## Evidence and its limits

- [OASIS CAP 1.2 §3.2.1](https://docs.oasis-open.org/emergency/cap/v1.2/CAP-v1.2-os.html): an Update supersedes, and a Cancel cancels, the earlier messages identified in its `references`. Each reference is a `(sender, identifier, sent)` tuple. These are directed message relationships; the standard does not say that every message sharing a reference is cancelled together. CAP permits multiple information and area blocks (§§3.2.2 and 3.2.4); it does not define an application-specific algorithm for mapping every partial NWS segment to a household incident.
- The current [NWS partial cancellation instructions](https://www.weather.gov/vtec/PartialCAN) describe reducing the polygon of a continuing warning and generating separate VTEC CAN and CON segments when a county/parish is removed. VTEC segment actions and CAP message types are different fields; neither may be substituted for the other.
- The [NWS alerts service change log](https://www.weather.gov/documentation/services-web-alerts) documents a historical correction to references to include prior messages, with flood warnings referencing the prior message because of long histories. The [2017 NWS CAP guide, p. 12](https://www.weather.gov/media/alert/CAP_v12_guide_05-16-2017.pdf) described referencing active messages impacted by an update or cancellation. The [2023 NWS CAP training, p. 8](https://www.weather.gov/media/wrn/calendar/2023NWS-CAP-User-Training.pdf) distinguishes direct NWS messages, which may have multiple references, from the IPAWS subset, which has at most one. These documents do not guarantee that a particular API response includes complete history or that every exceptional series follows one pattern. The older guide's restriction on Cancel usage is not a current guarantee; the observations below include actual Cancel messages.
- An anonymous NWS API snapshot retrieved approximately 2026-11-16 21:47 UTC supplied the projected public records in [`tests/fixtures/cap/nws-observed-segments.json`](../../tests/fixtures/cap/nws-observed-segments.json). Two same-time cold-weather Updates reference the same earlier message but describe different areas; two fog Cancels reference the same earlier message while describing different areas and times. The later fog Cancel also references another message. All four have null geometry. These observations demonstrate why shared ancestry cannot itself identify one current segment or establish that the entire shared predecessor's geographic scope ended. They do not supply the missing predecessors, establish complete history, prove all segment relationships, or provide a generic geographic matching algorithm. The fixture is a projection, not a complete API payload or a production incident replay.

## Conservative processing policy

1. Preserve the message identity tuple and directed references, including references whose target is absent. Check sender, identifier and sent consistently rather than treating identifier similarity as proof of identity. Reject or mark ambiguous malformed or conflicting identities. A grouping structure can aid deduplication but must not itself authorize cancellation or suppression across sibling branches.
2. Apply an Update or Cancel as evidence concerning its explicitly referenced earlier messages. A reference alone does not establish that a different, unreferenced successor or sibling was cancelled. In particular, a root-only Cancel cannot by itself close every descendant or a continuing segment. Do not infer branch or geographic cancellation merely from VTEC equality, intersecting UGCs, area names, or timestamps. The source evidence does not resolve every partial-area mapping even for a directly referenced predecessor; where the affected household scope cannot be established, preserve that uncertainty and withhold pending actions whose correctness cannot be established, rather than declare the entire geographic incident cleared.
3. A missing referenced message does not justify reconstructing its content. Persist the cancellation evidence, relevant identity and known scope so a delayed exact replay is not treated as fresh. If scope is unresolved, retain that fact and prevent an uncertain stale replay from producing output; keep independently supported siblings available for their own eligibility assessment. Surface partial/degraded health, and never label uncertainty, feed absence, or expiry as an affirmative all-clear. Reconcile when later authoritative records actually resolve it.
4. Compare actual message identities and issue times, independently of arrival order. A stale Cancel naming only an earlier root does not establish cancellation of a later unreferenced successor. A delayed message known to be affected by a later scoped cancellation must not resurrect that cancelled action. Equal or inconsistent timestamps, incomplete identities, cross-branch references and partial scope can make ordering or effect ambiguous; quarantine or otherwise withhold the affected action and report partial health instead of manufacturing an ordering or suppressing unrelated verified alerts.
5. A later Update explicitly referencing a Cancel is new evidence, not an automatic alarm or automatic dismissal. Evaluate its status, identity, times, geometry, rule, window and action history independently. An unreferenced later message sharing only an ancestor is a separate candidate, not a proven resurrection. Preserve pending-target rechecks and both live gates. A cancellation, including an upgrade of an older alert, is not proof that the underlying hazard ended.
6. Persist cancellation evidence and scope across restarts for at least the entire period in which the application may accept a replay or perform an action based on the affected message. Bound storage with an explicit, tested horizon consistent with those acceptance rules; expiry of a short-lived Cancel message alone is not a safe tombstone horizon. The Home Assistant integration enforces a seven-day maximum acceptance age (`MAX_ACCEPTANCE_AGE`) and matching seven-day cancellation-evidence retention horizon from the latest timestamp in a cancellation component, after which absent expired components lose tombstone protection and age out under the bounded journal cap. If history is lost, truncated, overflows, or cannot cover that horizon, withhold all output and report degraded health (`degraded_reason`, `degraded_at`, `degraded_until`) while continuing collection until the triggering condition is absent and either the seven-day acceptance horizon clears uncorrupted degradation on a clean poll or an administrator provides a one-shot non-future `acknowledge_degraded_at` at or after the latest `degraded_at` (an ongoing trigger refreshes `degraded_at` and `degraded_until` on each poll; a corrupted journal `malformed_store` withholds collection and output until repaired or replaced). Alerts first qualifying while degraded and undelivered pre-degradation targets remain eligible for evaluation once degradation clears without duplicating prior deliveries. No universal retention duration follows from CAP itself.

These are conservative application decisions, not assertions that NWS guarantees complete history, that every branch is automatically recoverable, or that a service call proves anyone received an alert. Independent official channels remain necessary. Controlled production replay, authoritative clarification of all branch cases, and physical commissioning have not been performed.
